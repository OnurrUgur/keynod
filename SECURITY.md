# Security

Keynod keeps secret values in the macOS Keychain behind Touch ID, and releases them to a command only after you approve that command on your Mac or your paired iPhone. This page says what that protects and what it does not.

## Threat model

**Keynod protects against:**

- **Secrets at rest being read without you.** Concealed values are only in the Data Protection Keychain, each item gated by user presence (Touch ID or your login password). They are never written to `vault.json`, logs, or iCloud.
- **Accidental verbatim leaks into agent output.** `keynod run` replaces secret values with `<concealed>` in output that is not a terminal, and `keynod get` refuses to print a value when Claude Code is in the caller's process tree.
- **A vault list changed behind the app's back, in a Team-signed build.** The title and field an approval names come from `vault.json`, but the value it releases is the Keychain item with that field's id. A process of yours could relabel a valuable field's id as a harmless one and get the app to load the file (kill it and let `keynod` restart it, or start a second copy on a prepared folder). `vault.json` is sealed with an HMAC-SHA256 under a key in the app's keychain access group. The seal covers the whole list: secret ids, titles, field ids and labels. A list whose seal doesn't check, or that has none, is shown in the app, but the `keynod` command releases and deletes nothing until you check it and choose **Trust Current Vault…** (Touch ID). Only one copy of Keynod runs at a time (a lock in the data folder, and Launch Services by bundle id). A Release build ignores `KEYNOD_DATA_DIR` and builds the data folder from the account's home folder, not from `HOME`.
- **Forged approvals or answers arriving through iCloud.** Requests and answers between Mac and iPhone are signed with keys created at pairing time (the iPhone's live in its Secure Enclave), are bound to one request, and expire.
- **Other programs on the socket, in a Team-signed, hardened build.** Two checks, both ways. First, the peer's code must satisfy the app's own designated code requirement, checked through the kernel's audit token. Second, every request and answer is sealed with a channel key that lives in the app's keychain access group, so only code signed into that group can read it. The signature check alone can be raced (a process connects, writes, then execs the real binary in the same pid). The channel closes that race: the app processes nothing that doesn't open with the key. A program that takes over the socket path while Keynod is not running gets nothing and can't approve Claude Code prompts.

**Keynod does not protect against:**

- **What an approved command does with the secret.** It can print it encoded (`base64`), write it to a file, or send it anywhere. Read the command in the approval dialog. It shows the real file `run` will execute (symlinks resolved; its file name always in full, only the middle of its folder may be shortened), its arguments as they run (quoted, with line breaks shown), and the file `inject` will write. Every field it releases and the command's arguments (or `inject` destination) must fit in full; a request that wouldn't fit is refused. A command or `inject` destination holding invisible or control characters is refused, since the dialog couldn't show it as it runs or writes.
- **What an approved command reads.** The approval covers the command line, not the files it reads: a script, a `Makefile` or a `package.json` can change after you approve. Inside Claude Code every `run` and `inject` therefore asks again; there is no repeat window. Outside it, the identical command line from the same shell may repeat for 5 minutes without asking (same environment, program file, directory and purpose), and Keynod doesn't recognise other agents, so with them a changed script runs unprompted within that window. The window ends when the screen locks or the Mac sleeps.
- **What the caller's environment does.** An approved command runs with the caller's environment (`PATH`, `NODE_OPTIONS`, `DYLD_*` for unhardened programs, and so on). The dialog doesn't show it. A changed environment asks again, but the first approval trusts whatever environment the caller had.
- **A determined agent or script.** Output masking and the Claude Code `get` guard are guardrails, not boundaries. They catch accidents, not a process that encodes a value or leaves Claude's process tree.
- **Other processes running as you.** They can read `vault.json` and `keynod list` metadata (titles, descriptions, tags, field labels, plain fields), and the environment and temporary files of a command started by `keynod run`. They can also put back an older sealed copy of `vault.json`: it is still your own list from that time, so a secret deleted since reappears without a value.
- **Apple's view of request metadata.** iPhone approvals and Claude Code questions travel through your private iCloud database and Apple's push service. Secret values are never part of them, but caller, command, directory, field names and question text are, in fields that are signed but not encrypted. Before a question leaves the Mac, secrets that Key Catcher recognises are replaced with a marker. That is best effort: secrets of an unknown shape, and pictures attached to a question, go as they are.
- **Anything, in builds without a Team ID.** Unsigned and ad-hoc builds have no keychain access group. The Vault can't store secrets, and the app tells you so at launch. The channel key and the vault seal key are then `0600` files in the data folder that any process of yours can read, so the socket and the seal are open to them, and code can be injected into an unhardened build.
- **Other builds signed by the same team.** A Debug build signed by your team shares the keychain access group and satisfies the designated requirement, so it counts as the app: it can read the channel and seal keys, and it honours `KEYNOD_DATA_DIR`. A hardened Release app does refuse a peer that is debuggable (`get-task-allow`) or unhardened.
- **The stay-awake feature's sudoers rule.** The optional "stay awake" switch relies on a narrow sudoers rule for `pmset`. Anything running as you can use that rule too.
- **Blocking the socket.** A process running as you can hold or replace `keynod.sock`, or open a connection and never finish it (there is no read timeout, and one approval dialog shows at a time), so the `keynod` command and the Claude Code hooks stop working. That denies service only: nothing is sent to it and nothing is released.
- **A replayed iPhone command after a restart.** The Mac remembers which signed iPhone commands (`lock`, `sleep`, stay awake on or off) it has run only until it quits. Someone with write access to your iCloud database can save one again within its 10 minutes after Keynod restarts. That is a nuisance, not a release: those commands carry no secrets.
- **A narrow race after the last check.** `run` checks the program file's identity again just before it starts it, and `inject` checks where the opened file really is before writing. A process that replaces the program or a destination folder in the moment between that check and its use can still win.

## Storage

- **Metadata (`vault.json`)**: titles, descriptions, `#tags`, field labels and plain fields, in `~/Library/Application Support/Keynod/` (folder `0700`, file `0600`). Concealed values are stripped when the file is written. The file is `{"secrets":[…],"seal":"<HMAC-SHA256>"}`; the seal key (32 random bytes) sits in the Data Protection Keychain next to the channel key, or in the `0600` file `vault.key` when the keychain answers -34018. While the list is not trusted, the app saves it without a seal, so it stays untrusted until you confirm it.
- **Concealed values**: Data Protection Keychain (`kSecUseDataProtectionKeychain`), `kSecAttrAccessibleWhenUnlockedThisDeviceOnly`, `.userPresence`.
- **Hardened runtime**: Team-signed builds enable it, so `DYLD_INSERT_LIBRARIES` can't load code into Keynod and use its keychain access group.

## CLI

- The socket `keynod.sock` is `0600` inside the `0700` data folder. Its descriptors are close-on-exec.
- **Peer check, both ways**: same user id, and the peer's code (looked up by its audit token) must satisfy this build's designated requirement. A hardened app without `get-task-allow` also requires that of its peer. If the app can't work out its own requirement, it refuses every request.
- **Channel**: after the peer check, both sides exchange 32-byte nonces. Two keys, one per direction, are derived with HKDF-SHA256 from the channel key and both nonces. The request and the answer are each one ChaChaPoly frame with a counter nonce, so a frame from another connection, a repeat, a changed byte or plain text never opens, and nothing unopened is processed. The `keynod` command shows a plain-text refusal only as a generic "not this build" error.
- **Channel key**: 32 random bytes. In a build whose keychain works it sits in the Data Protection Keychain (`AfterFirstUnlockThisDeviceOnly`, no user presence); the app creates it before listening and the command only reads it. Without a keychain access group (the keychain answers -34018) it is the `0600` file `channel.key` in the data folder. A build whose keychain works never uses the file, and any other keychain error stops the CLI.
- **Caller details**: the sealed request names the caller's pid, which must equal the connection's. It also carries a digest of the caller's environment; for `run`, the real file it will execute (with the path its lookup found, and the file's device, inode, size, and modification and status-change times); for `inject`, the file it will write. The app reads arguments, working directory and parents for that pid from the kernel, then checks that the process is still the same one. It refuses `run`, `inject`, `get`, `secret add` and `secret delete` when that fails, or when the arguments disagree with the reported program or destination. `run`, `inject`, `get` and `secret delete` also wait for a trusted `vault.json` (see the threat model).
- **Running and writing**: the `keynod` command finds the program itself (like `posix_spawnp`), resolves it to the real file, and executes exactly that file. Just before starting it, the command checks that the file's identity hasn't changed since the request; if it has, it runs nothing. For `inject`, symlinks in the destination's folder are shown resolved. The file itself is opened with `O_NOFOLLOW`, and before a byte is written (or an existing file is emptied), its real path (`F_GETPATH`) must equal the approved destination. Otherwise nothing is written, and a file this call created is removed.
- **Approval windows**: `get`, `secret add` and `secret delete` always ask, and so do `run` and `inject` whenever Claude Code is in the caller's process chain. Otherwise `run` and `inject` skip the prompt for 5 minutes only for the identical command line (every argument), purpose, field set, environment, program file (path and identity) or destination, and directory, from the same parent process (pid and start time). A detached caller (parent launchd) or one whose details are missing always asks. Windows are dropped on screen lock and sleep, and are separate from the app window's own unlock.
- **Claude Code detection** looks at whole executable names and path components (`claude`, `…/claude/versions/<version>`, `@anthropic-ai/claude-code`). A process that detaches from Claude's tree is not detected.

## iPhone approvals

- Messages use your own private CloudKit database. There is no Keynod server.
- For each concealed field the Mac keeps a second copy encrypted to the iPhone's Secure Enclave `field` key (P-256 ECDH, HKDF-SHA256, AES-GCM, label `keynod.field.v1|<field-id>`). On approval the iPhone wraps only the requested field keys to a one-time reply key (`keynod.reply.v1|<req-id>|<field-id>`) and signs the answer. Replayed or expired answers are rejected.
- The `approve` and `field` keys live in the Secure Enclave with `.biometryCurrentSet`. Changing Face ID enrollment invalidates them.
- **Pairing**: both screens show a six-digit code derived from the iPhone's reply. The Mac's signed acknowledgement names that reply by its SHA-256, and the iPhone accepts it only if it matches its own reply. So a reply swapped in with the same code, by someone holding the pairing code and write access to your iCloud, can't leave the real phone believing it is paired.
- **Claude Code permission prompts** go to the phone only when the whole tool call fits the card (summary up to 300 characters, details up to 1,500), because Allow covers all of it. A longer call stays with Claude Code's own prompt on the Mac.
- Control, invisible (zero-width, variation selectors) and bidirectional characters are removed from caller, command and question text first. Secrets Key Catcher recognises are replaced next, and the length is capped last. The iPhone's copy of an approval's command and summary is built from the uncut text in that order, so a secret can't straddle the cut. The Touch ID text on the Mac is not redacted.

## Backup

`Export Vault…` writes a `0600` `.keynodvault` file sealed with AES-256-GCM, keyed by PBKDF2-HMAC-SHA256 (600,000 iterations, random 16-byte salt). Import skips a secret that already exists, and one whose field ids are already in use (it would replace another secret's value), and says how many it skipped.

## Known limitations

- No read timeout on the socket: a stalled connection holds a worker thread until it closes (denial of service only; see above).
- Handled iPhone commands are remembered in memory only, so one can be replayed within its 10 minutes after a restart (a nuisance; see above).
- Locking the screen from the iPhone uses a private macOS function (`SACLockScreenImmediate`).

Please report security issues privately through GitHub Security Advisories, not in a public issue.
